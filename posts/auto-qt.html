Auto autónomo con integración Qt

Código: se va a cargar en GitHub próximamente

Lo armé en 2021 para la materia Informática 2. Es un auto que se maneja por WiFi desde una aplicación en Qt en la computadora, y que además tiene un modo autónomo en el que avanza solo y esquiva los obstáculos que encuentra. El profesor nos felicitó y nos seleccionó para presentarlo al año siguiente.

Comunicación: el auto crea su propia red

El ESP8266 se configura como access point y abre un servidor TCP en el puerto 8888. La computadora ve el auto como una red WiFi más: se conecta, abre un socket contra el servidor y desde ahí le manda comandos. El microcontrolador le habla al ESP8266 por UART con comandos AT:

Extracto de source/ESP8266.h

#define COMANDO_CWMODE			ESP8266_enviaAT("AT+CWMODE=2\r\n")
#define COMANDO_SOFTAP			ESP8266_configuraSoftAP("ESP8266-Wifi", "pas123", "3", "0")
#define COMANDO_CIPMUX			ESP8266_enviaAT("AT+CIPMUX=1\r\n")
#define COMANDO_CIPSERVER		ESP8266_enviaAT("AT+CIPSERVER=1,8888\r\n")

Los comandos que manda la aplicación son letras sueltas dentro de una trama con un carácter inicial y uno final, para poder distinguirlos de las respuestas del módulo:

El firmware: un lazo cooperativo

No usé un sistema operativo. El programa principal es un lazo que atiende tres cosas por turno, apoyado en un sistema propio de temporizadores por eventos (timer.c) para todas las esperas, de modo que nada se queda bloqueado:

Extracto de source/auto4.c

while(1)
{
    TimerEvent();              // temporizadores por eventos
    Verificar_datos();         // comunicación con el ESP8266
    Movimiento_Auto(modo);     // control del auto: manual o automático
}

Modo autónomo

El modo autónomo es una máquina de estados (REPOSO_AUTO → ESPERO_A_MEDIR → DECIDO_ACCION → GIRANDO_AUTO / GIRANDO_SERVO). Mide la distancia al frente con el ultrasonido; si hay más de 20 cm libres, avanza. Si no, frena y usa el servo para mirar primero a la derecha y después a la izquierda:

Extracto de Movimiento_Auto() en source/Movimiento_Auto.c

case FRENTE:
    if (distancia >= DISTANCIA_MAX_OBJETO)
    {
        //Si hay suficiente espacio de frente para avzanzar, avanzo
        AVANZAR_AUTO;
        //Vuelvo a medir
        estado = REPOSO_AUTO;
    }
    else
    {
        DETENER_AUTO;
        //Miro primero a la derecha
        DETECCION_DERECHA;
        AnguloServo = DERECHA;
        ServoYaGiro = FALSE;
        t_GirarServo();
        estado = GIRANDO_SERVO;
    }
    break;

Con las dos distancias, el auto elige el lado con más espacio. Si ninguno de los dos tiene lugar, da media vuelta:

Extracto de Decido_Movimiento()

if (distanciaDerecha >= distanciaIzquierda && distanciaDerecha >= DISTANCIA_MAX_OBJETO)
{
    //Si hay mas espacio a la derecha, giro para la derecha
    GIRAR_DERECHA;
    t_GirarAuto();
}
else if (distanciaDerecha < distanciaIzquierda && distanciaIzquierda >= DISTANCIA_MAX_OBJETO)
{
    //Si hay mas espacio a la izquierda, giro a la izquierda
    GIRAR_IZQUIERDA;
    t_GirarAuto();
}
else if (distanciaDerecha < DISTANCIA_MAX_OBJETO && distanciaIzquierda < DISTANCIA_MAX_OBJETO)
{
    //Si no tengo espacio para avanzar a los costados, doy media vuelta para retroceder
    RETROCEDER_DERECHA;
    t_RetrocederAuto();
}

Los giros están temporizados: unos 600 ms para 90° y 1 s para dar la vuelta. La medición usa el timer SCT y una interrupción de pin para medir el tiempo que tarda el eco, y el servo se maneja con PWM del CTIMER.

El encoder casero

Para saber cuánto recorrió el auto armé un encoder con un sensor infrarrojo de presencia, que modifiqué para que el fototransistor quedara del otro lado de la rueda. La rueda mide 66 mm y tiene 5 radios, así que el sensor cambia de estado 10 veces por vuelta, y cada cambio equivale a unos 20,7 mm. Cada cambio se confirma con un antirrebote antes de contarlo:

Extracto de Debounce_Infrarrojo() en source/Infrarrojo.c

if(ESTADO_INFRA != estado_Anterior)
{
    debounce++;
    if(debounce == N_DEBOUNCE)
    {
        debounce = 0;
        estado_Anterior = ESTADO_INFRA;
        contador_Infra++;
    }
}
else
{
    debounce = 0;
}

Un problema práctico: el LED infrarrojo era tan potente que atravesaba el plástico de la rueda. Lo resolví envolviendo el plástico con cinta negra. El auto le informa a la computadora la distancia recorrida cada dos segundos, y solo cuando cambió.

La aplicación en Qt

La interfaz de la computadora la hice en Qt 5, con los módulos de widgets y de red. Se conecta al auto como cliente TCP: abre un socket contra 192.168.4.1:8888 (la IP por defecto del ESP8266) y le manda los comandos como tramas cortas, con $ al inicio y / al final.

La aplicación permite:

  • Conectarse y desconectarse, con un indicador de estado (rojo, amarillo o verde).
  • Manejar el auto con botones o con las flechas del teclado. El auto se mueve mientras se mantiene presionado y frena al soltar. Se pueden combinar teclas: flecha arriba más izquierda hace girar al auto hacia la izquierda avanzando, y lo mismo retrocediendo.
  • Activar y desactivar el modo autónomo. Con el modo activo, el teclado deja de mandar comandos.
  • Ver una imagen del auto que cambia según lo que hace (avanzar, retroceder, girar, frenar, modo autónomo o sin señal). En modo autónomo la imagen sigue las acciones que el auto informa.
  • Ver la distancia recorrida y reiniciarla con un botón.

El manejo del teclado combina dos variables, el sentido (avanzar o retroceder) y el giro, y de la combinación sale el comando:

if(sentido ==  RETROCEDER)

}

Del otro lado, la aplicación recibe dos tipos de mensajes: la distancia (+NNNNN/, en milímetros) y la acción actual del auto ($f/, $l/…), y actualiza la pantalla en consecuencia:

La interfaz usa una hoja de estilos oscura propia y el logo de la UTN.

Resultados

Los resultados cumplieron por el lado del control remoto: el auto respondía a los comandos que mandaba la aplicación de Qt por WiFi.

El modo autónomo, en cambio, no funcionó correctamente. Hubo dos causas:

  • Sensores poco precisos. Las mediciones del ultrasonido y del encoder casero no tenían la exactitud que el modo autónomo necesitaba para decidir bien.
  • Debilidades mecánicas. El auto estaba desbalanceado hacia un lado y se tiraba más para un lado que para el otro. En el firmware llegué a ajustar a mano la potencia de los motores para que fuera recto (hay una constante POT_AJUSTADA con ese propósito), pero la corrección por software no alcanzó a compensar un problema que era del chasis.

Aprendí que un buen algoritmo no compensa una mecánica débil ni sensores imprecisos. Si el auto no avanza recto, ninguna decisión del software llega a donde se esperaba.
